# 3. Finish

새 기능을 만들지 않는다. 사람이 남은 시간을 말하지 않았으면 한 줄로 묻는다. 시간이 부족하면 1, 3, 4번을 먼저 끝낸다. 제출 버튼은 사람이 누른다.

## 1. 원문 대조

과제 원문을 **다시 읽는다.** `docs/TASKS.md`만 보지 않는다. 빠진 요구사항이 있으면 R을 추가한다. 요구사항 표의 구현 위치, 실행한 검증과 결과, 상태(통과·실패·미확인)를 채운다. 실행하지 않은 것은 미확인이다.

추가로 문서 사이의 불일치를 찾는다: 결정(D)이 구현에 반영되지 않은 곳, 담당자 용어와 다른 용어, 근거 없는 수치.

**제출 문서의 주장을 점검한다.** 문장마다 파일, 실행 결과, 커밋 중 하나로 뒷받침되는지 확인하고, 근거가 없거나 실제로 하지 않은 일이면 문서를 고친다.

심각도 순으로 고친다.

- 치명: 필수 기능 없음, 실행 불가, 제출 경로 틀림, G3 실패
- 높음: 필수 기능의 주요 예외 실패
- 낮음: 나머지. 시간이 남을 때만 고친다.

## 2. 처음부터 실행

- 문서에 적은 실행 명령 그대로 다시 실행한다. 서버 재시작은 사람에게 요청한다.
- `scripts/check_scale.*`과 `scripts/check_scenarios.*`를 다시 실행하고 핵심 API를 `curl`로 확인한다.
- 사람용 검수 목록을 8개 이내로 준다: PORT와 경로, 누를 것, 기대 결과. 역할별 핵심 흐름을 포함한다. 사람의 답을 받기 전에는 사람 확인 완료로 적지 않는다.

## 3. 제출물

- 과제가 요구한 문서(계획, 협업 기록 등)가 지정된 이름과 경로에 있는지 확인한다. 작업 중 기록을 옮겨 채우되, 없는 내용을 꾸미지 않는다.
- 필수 파일의 경로와 이름을 `ls`로 확인한다. 실행 방법이 문서에 있는지 확인한다.
- 디버그 코드, 임시 파일, 키·토큰, 필요 없는 대용량 파일이 없는지 확인한다.
- `finish: 제출 준비` 형식으로 커밋한다.

## 4. 서술형 대비 요약

`docs/BRIEF.md`를 두 페이지 이내로 쓴다. 후속 서술형은 제출물과 작업 기록을 바탕으로 출제되고 AI를 쓸 수 없으므로, 사람이 직접 읽고 자기 말로 설명하기 위한 문서다. 파일, 실행 결과, `git log`에 있는 사실만 쓰고, 모르는 것은 모른다고 쓴다. 모범 답안은 쓰지 않는다.

1. 데이터 흐름과 모듈: 입력부터 저장, 화면까지 모듈별 입력, 출력, 책임, 맡지 않는 일, 파일 위치
2. 검증한 것과 가정한 것: 표로 구분하고, 다른 사람이 확인할 파일과 명령을 함께 적는다
3. 핵심 결정: D 항목별 선택, 근거, 버린 대안, 담당자 답
4. 변경·경계 시나리오: 실제로 돌린 결과와 깨지기 쉬운 곳
5. AI 설명 없이 확인하는 법: 독립 검사, 기준안 비교 수치, 규모가 커지거나 조건이 까다로워지면 먼저 볼 곳
6. AI 협업: 요청 원문, 받아들인 것, 고친 것, 버린 것과 각각의 근거
7. 실수와 수정: 무엇이 틀렸고 어떻게 알았고 어떻게 고쳤나
8. 제출 문서에 적힌 주요 주장과 근거 위치

시간이 부족하면 1, 2, 6번만 쓴다.

## 5. 사람에게 넘기기

아래를 그대로 안내한다.

1. `docs/BRIEF.md`를 직접 읽는다. 확정 후에는 다시 볼 수 없다고 가정한다.
2. 에디터의 저장 상태가 "저장됨"인지 확인한다.
3. "제출하고 문제풀기"로 미리보기를 연다. 미리보기 목록은 일부만 보일 수 있다.
4. "제출물 확정하고 문제풀기"를 누른다. 확정 후에는 수정할 수 없다.
5. 서술형은 질문의 전제가 실제 구현과 다르면 차이를 밝히고 자기 말로 답한다.
6. 완료 화면에서 제출 ID, 시각, 파일 수, 크기를 확인한다.
