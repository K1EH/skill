# 2. Build

순서는 설계 고정 → 핵심 로직 → 규모 검증 → API → 화면이다. 화면을 먼저 만들지 않는다.

`docs/DATA_PROFILE.md`, `docs/DECISIONS.md`, `docs/TASKS.md`를 먼저 읽는다. 프로파일이 없으면 먼저 만든다(G1). 사람이 남은 시간을 말하지 않았으면 한 줄로 묻는다.

## 1. 설계 고정 (G2)

`docs/DECISIONS.md`의 "설계 고정"을 채운다.

- 기준 데이터와 나머지 데이터의 처리. 결정 ID를 근거로 단다.
- 결과별 예상 범위. **입력 수와 제약에서 산식으로 유도한다.** 예: 입력 N건, 항목당 정원 C면 최소 ⌈N/C⌉개. 산식을 세울 수 없으면 담당자 질문으로 돌린다.
- 숫자 완료 조건: 범위, 배정률처럼 실행해서 판정할 수 있는 조건
- 멈춤 조건: 어떤 결과가 나오면 진행을 멈추고 알릴 것인가

기술 스택은 과제가 지정한 것을 쓴다. 지정이 없으면 작업 공간에 설치된 런타임에서 가장 단순한 구성을 고른다.

**설계 검수를 한 번 받는다.** 사람에게 `review` 탭의 별도 Codex 세션이나 서브에이전트에 보낼 요청문을 준다. 요청문은 과제 원문과 `docs/DECISIONS.md`를 읽고 누락, 모순, 근거 없는 수치를 찾아 달라는 내용이다. 지적마다 원문이나 데이터로 직접 확인해 수용·수정·폐기를 정하고 `docs/AI_LOG.md`에 적는다. 지적을 그대로 믿지 않는다. 업무 규칙에 관한 지적은 담당자에게 묻고, 답을 받지 못하면 결정이 아니라 가정 표에 적는다. 검수로 범위를 고치는 것은 사람의 OK 전에 끝낸다. OK 이후의 변경은 G3 규칙을 따른다.

사람에게 15줄 이내로 보여주고 OK를 한 번 받는다: 기준 데이터, 결과 범위, 데이터 모델 핵심, 화면 목록, 제외한 것, 검수에서 받아들이거나 버린 것. OK를 받으면 상태와 함께 커밋한다.

## 2. 작업 계획

`docs/TASKS.md`에 작업 4~8개를 적는다. 각 작업에 관련 R, 파일, 검증 명령만 쓴다. 순서는 고정이다: 핵심 로직과 G3 → 저장과 API → 일반 사용자 흐름 → 관리자 흐름 → 다듬기. 작업마다 계속할지 묻지 않고 이어간다.

## 3. 핵심 로직과 규모 검증 (G3)

핵심 로직을 전체 실데이터로 실행한다. `scripts/check_scale.*`을 만들어 **실제 출력값을 세어** 판정한다. 로직을 다시 계산하지 않는다.

- 결과별 실제 수, 예상 범위, PASS/FAIL
- 분포: 항목당 건수의 최소·중앙값·최대
- 커버리지: 어디에도 배정되지 않은 입력 수
- 제약 위반 수: 요구사항의 제약을 생성 로직과 별개의 코드로 출력 파일에서 직접 검사한 결과
- 기준안 비교: 휴리스틱이나 최적화를 넣었다면 실제로 쓸 만한 단순한 방식과의 전후 수치. 기준안을 일부러 약하게 잡지 않는다.
- 결과 샘플 5개
- FAIL이 하나라도 있으면 0이 아닌 종료 코드

FAIL이면 **즉시 멈추고** 다음을 보고한다. 사람이 재촉해도 화면 작업으로 넘어가지 않는다.

```text
G3 실패: [결과] 실제 N개 / 예상 A~B개
유력한 원인: (입력 필터, 산식, 알고리즘 순으로 확인한 결과)
제안: (수정안 한 줄)
```

범위를 결과에 맞춰 고치지 않는다. 산식이 틀렸다면 근거를 D 항목으로 남기고 사람의 OK를 받는다. 로직을 바꿀 때마다 다시 실행한다. 틀린 설계를 고쳤다면 "실수와 수정"에 적는다.

## 4. 저장, API, 사용자 흐름

- 필수 흐름 하나를 입력부터 결과까지 먼저 연결하고 나머지를 붙인다. 실제 데이터를 쓰고 목업으로 대체하지 않는다.
- 서버 규칙은 AGENTS.md를 따른다. Vite는 `server.allowedHosts: true`, Next.js는 `allowedDevOrigins`처럼 프록시 호스트를 막는 설정이 있는지 확인한다.
- API는 `curl`로 검증하고 결과를 `docs/TASKS.md`에 짧게 적는다.

## 5. 변경·경계 시나리오

`scripts/check_scenarios.*`로 3~5개를 실제로 돌려 `docs/TASKS.md`의 "시나리오 결과"에 적는다. 추측으로 적지 않는다. 원본 데이터는 바꾸지 않고 복사본이나 필터로 실행한다.

- 입력 조건이 바뀔 때: 기간, 상태 값, 관리자가 수정한 결과가 재생성에서 어떻게 되는가
- 제약을 넘을 때: 정원·용량 초과처럼 규칙을 만족할 수 없는 입력
- 대상이 없을 때: 선택 범위의 입력이 0건
- 규모가 커질 때: 입력을 2배, 10배로 늘린 실행 시간과 결과 수

오류로 죽거나 조용히 틀린 결과를 내면 고치거나, 시간이 없으면 "깨지기 쉬운 곳"으로 기록한다.

## 6. 화면

시안을 여러 개 만들지 않는다. 대신 코드 전에 짧은 계획을 세우고 실데이터로 확인한다.

**계획 (15줄 이내, `docs/TASKS.md`에 적지 않고 대화로 보여준 뒤 바로 진행):**

- 화면마다 "누가 무엇을 판단하려고 보는가" 한 줄
- ASCII 와이어프레임
- 색 4~6개, 글꼴, 간격 토큰. 업무 맥락에 맞게 고른다.

그다음 과제 원문과 대조하고, 빠진 필수 항목이 있으면 고친 뒤 구현한다.

**구현 규칙:**

- 첫 화면은 요약 수치와 판단에 필요한 것을 보여준다. 전체 목록을 쏟아내지 않는다.
- 항목이 50개를 넘는 목록은 기본을 그룹·요약으로 두고 검색, 필터, 페이지 이동을 붙인다.
- 지도, 차트처럼 표시량이 많은 요소도 기본 표시를 선택 항목이나 상위 항목으로 줄인다.
- 일반 사용자 화면은 자기 것만 보여주고 관리자 화면과 분리한다.
- 화면마다 주요 행동은 하나다. 빈 상태, 로딩, 오류를 만든다.
- 문구는 담당자가 쓴 업무 용어로 쓴다. 버튼은 실제 동작 이름으로 쓴다.
- **전체 실데이터로 확인한다.** 샘플 몇 건으로 보기 좋은 것은 통과가 아니다.

스크린샷 도구가 이미 있거나 빠르게 설치되면 직접 보고 고친다. 아니면 사람에게 PORT, 경로, 볼 것을 알려주고 Browser에서 확인을 받는다.

## 7. 서브에이전트 위임

세션당 최대 2개(메인 제외)이며 요청해야 생성된다. G3 통과 후, 공용 계약이 정해진 뒤에만 쓴다. 2개가 이미 실행 중이면 끝나기를 기다리거나 메인이 직접 한다.

- 적합: 서로 다른 파일의 화면, 테스트 작성, 요구사항 누락 검토
- 부적합: 설계, 핵심 로직, 같은 파일을 건드리는 작업, 결과를 기다리는 동안 메인이 할 일이 없는 작업

프롬프트에는 수정 가능한 파일, 목표, 지켜야 할 공용 계약, 기대 출력(변경 파일, 실행한 명령과 결과)을 적는다. 필요한 맥락은 메인이 직접 적어 준다. 모델은 복잡한 작업에 `gpt-6.1-sol`, 좁고 빠른 작업에 `gpt-6-luna`를 쓰되 환경에서 제공될 때만 지정한다.

"수정하지 말라"는 지시는 샌드박스가 아니다. 끝나면 `git status`와 `git diff`로 실제 변경을 확인하고 직접 실행해 본다.

## 8. 막혔을 때

재현 → 원인 확인 → 최소 수정 → 재확인 순으로 한다. 같은 문제에 두 번 실패하면 세 번째 시도 전에 현상, 가설, 다음 안을 3줄로 사람에게 알린다. 응답 지연과 모델·API 오류를 구분하고, 같은 요청을 반복하지 않는다.

## 9. 마무리

필수 R이 모두 구현되면 G4에 따라 실행 결과를 확인하고 커밋한 뒤 `$3-finish`를 안내한다. 선택 기능은 필수와 검증이 끝나고 시간이 남을 때만 한다.
