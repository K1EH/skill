# 3. Core

화면을 먼저 만들지 않는다. 결과가 맞는지 숫자로 확인한 뒤에 넘어간다. PRD의 G2 상태가 승인이 아니면 `$2-prd`로 돌아간다. 사람이 남은 시간을 말하지 않았으면 한 줄로 묻는다.

## 1. 작업 계획

`docs/TASKS.md`에 쓴다. 구현할 사람은 내가 내린 결정을 모르므로, 결정만 적고 코드는 적지 않는다.

- 파일 구조: 만들거나 고칠 파일과 각 파일의 책임. 함께 바뀌는 것은 함께 둔다.
- 작업 4~8개. 각 작업에 관련 R, 파일, 앞뒤 작업이 의존하는 함수·API 이름, 검증 명령과 통과를 뜻하는 출력을 적는다.
- 순서는 고정이다: 핵심 로직과 G3 → 저장과 API → 주 사용자 흐름 → 나머지 역할의 흐름 → 다듬기.
- 작업 계획을 다 쓰면 요구사항마다 담당 작업이 있는지, 같은 함수를 다른 이름으로 쓰지 않았는지 확인한다.

작업마다 계속할지 묻지 않고 이어간다.

## 2. 핵심 로직과 결과 검증 (G3)

핵심 로직을 제공된 입력 전체로 실행한다. `scripts/check_core.*`을 만들어 **실제 출력값으로** 판정한다. 생성 로직을 불러오거나 다시 계산하지 않는다. PRD의 판정 기준에 맞는 것을 출력한다.

- 생성·배정 결과: 결과별 실제 수와 예상 범위, 항목당 건수의 최소·중앙값·최대, 어디에도 배정되지 않은 입력 수, 샘플 5개
- 규칙·상태 변화: 사례 표의 입력을 실제 로직으로 실행한 결과와 통과 수, 실패 사례의 기대값과 실제값
- AI·비결정 결과: 고정 예시 입력의 통과율과 실패 사례, 조건마다 코드로 판정한 결과. 사람이 읽어야 판정할 수 있는 항목은 미확인으로 표시한다. 예시를 보고 로직을 고쳤다면 그 통과율은 새 입력의 성능이 아니라고 적고, 가능하면 일부 예시를 떼어 두고 확인한다.

해당하면 다음도 포함한다.

- 제약 위반 수: 요구사항의 제약을 별도 코드로 직접 검사한 결과
- 기준안 비교: 근사 로직이나 최적화를 넣었다면 실제로 쓸 만한 단순한 방식과의 전후 수치. 기준안을 일부러 약하게 잡지 않는다.
- FAIL이 하나라도 있으면 0이 아닌 종료 코드

FAIL이면 **API·화면 작업을 즉시 멈추고** 다음을 보고한다. 사람이 재촉해도 API·화면으로 넘어가지 않는다.

```text
G3 실패: [항목] 실제 값 / 판정 기준
유력한 원인: (입력, 판정 기준, 로직 순으로 확인한 결과)
제안: (수정안 한 줄)
```

기준을 결과에 맞춰 고치지 않는다. 기준이 틀렸다면 근거를 D 항목으로 남기고 사람의 OK를 받는다. 코드가 승인된 PRD를 어긴 것이 원인이고 기준을 바꾸지 않는다면, 보고한 뒤 OK를 기다리지 않고 PRD대로 고쳐 다시 실행한다. 로직을 바꿀 때마다 다시 실행한다. 틀린 설계를 고쳤다면 "실수와 수정"에 적는다.

전부 PASS면 출력 요약과 함께 `core: G3 통과, 수치` 형식으로 커밋하고 `$4-build`를 안내한다.

## 3. 디버깅

**근본 원인을 찾기 전에는 고치지 않는다.** 증상만 고치는 것은 실패다. 시간이 없을수록 더 지킨다. 추측으로 고치는 것이 체계적으로 찾는 것보다 느리다. 오류, 실패한 검증, 이상한 결과 모두에 적용한다.

1. **원인 조사:** 오류 메시지와 스택을 끝까지 읽는다. 매번 재현되는 명령을 확보한다. `git diff`로 최근 변경을 본다. 구성 요소가 여러 개면 경계마다 들어오고 나가는 값을 찍어 어디서 깨지는지 찾는다. 나쁜 값이 어디서 왔는지 거슬러 올라가 출처에서 고친다.
2. **패턴 비교:** 같은 코드베이스에서 동작하는 비슷한 코드를 찾아 차이를 전부 적는다. "그건 상관없겠지"라고 넘기지 않는다.
3. **가설과 검증:** "X가 원인이다, 왜냐하면 Y다"로 하나만 적고, 변수 하나만 바꿔 확인한다. 틀리면 그 위에 덧대지 말고 새 가설을 세운다. 모르면 모른다고 말한다.
4. **수정:** 재현 명령이나 일회성 스크립트를 먼저 준비하고, 원인 하나를 고치고, 재현 명령과 기존 검증을 다시 돌린다. 하는 김에 다른 것을 고치지 않는다.

**두 번 실패하면 세 번째 시도 전에 현상, 가설, 다음 안을 3줄로 사람에게 알린다.** 세 번 실패했거나 고칠 때마다 다른 곳에서 문제가 나오면 설계가 틀린 것일 수 있으니 더 고치지 말고 설계부터 다시 본다.

이런 생각이 들면 1번으로 돌아간다: "일단 고치고 나중에 조사", "X만 바꿔 보자", "한 번에 여러 개 고치자", "아마 X일 것이다", "한 번만 더".

응답 지연과 모델·API 오류를 구분하고, 같은 요청을 반복하지 않는다.
