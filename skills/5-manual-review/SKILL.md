# Manual Review

사용자가 매뉴얼의 페이지와 항목을 가리켜 검수하고 수정을 요청할 수 있게 하라. 실제 구현, 설명, 확인 상태를 일치시켜라.

## 진행 깊이 선택

- 빠르게(quick), 표준(standard), 깊게(deep) 중 사용자가 지정한 모드를 적용하라. 기본은 표준이다.
- 작업 프로젝트의 docs/WORKFLOW_SETTINGS.md가 있으면 읽고 모드·남은 시간·개별 설정을 재사용하라. 현재 사용자의 명시적 요청을 가장 우선하라.
- 모드가 없으면 표준을 적용한다고 한 줄 알리고 진행하라. 사용자가 먼저 선택하겠다고 요청하면 세 모드 중 선택을 받아라. 이미 정한 모드를 반복 질문하지 마라.
- 선택·변경된 값은 파일 도구가 있으면 docs/WORKFLOW_SETTINGS.md에 짧게 기록하라. 파일이 없으면 새로 만들되 기존 설정의 다른 항목은 보존하라. 파일 도구가 없으면 대화에 기록하라.
- 아래 숫자는 자연어 기본값과 목표 예산이다. 자동 타이머나 프로그램의 강제 제한이 아니다. 실제 남은 시간을 확인할 수 없으면 사용자에게 받은 시간을 사용하고 추정임을 표시하라.
- 깊이를 줄여도 원문 필수 기능, 고정 ID, 명시적인 시안 선택, 실제 검증의 정직성은 유지하라. 시간 부족 때문에 필수 기능을 조용히 제외하지 마라.

| 모드 | 사용자 설명의 깊이 | 항목당 내용 |
| --- | --- | --- |
| 빠르게 | 짧은 검수용 매뉴얼 | 필수 흐름·최소 절차·기대 결과·확인 상태 |
| 표준 | 일반 사용자가 따라할 수 있는 매뉴얼 | 시작 화면·사전 조건·절차·주요 오류·검수 상태 |
| 깊게 | 예외와 복구까지 설명하는 매뉴얼 | 주요 경계 상태·역할별 차이·복구·문제 해결 추가 |

어떤 모드도 실제 구현된 필수 흐름의 항목을 생략하거나 고정 번호를 바꾸지 마라. 모드는 항목당 설명과 추가 검증 깊이를 조절한다. 빠르게 모드도 Markdown·읽기용 HTML과 번호 기반 수정 흐름을 유지한다. 실제 화면이 많으면 문서 제작·검수 시간이 늘어나며 최종 사용자 확인 시간을 별도로 남겨라.

## 조정 가능한 기본값 — 표준 모드 기준

- 기준 문서: docs/USER_MANUAL.md.
- 읽기용 매뉴얼: docs/USER_MANUAL.html. 문서와 같은 순서의 명시적인 페이지 패널·페이지 이동·항목 링크 제공.
- 범위: 실제로 구현된 사용자 흐름 전체. 페이지 수를 맞추려고 필수 기능을 생략하지 마라.
- 페이지당 항목: 보통 3~6개. 필요한 경우 한 기능을 여러 페이지로 나누라.
- PDF: 사용자가 요청하거나 제출 형식에 필요할 때만 추가하고 실제 인쇄 페이지 번호를 렌더링으로 확인하라.

## 실제 구현 확인

1. PRD, 실행 방법, 현재 코드, 기존 매뉴얼과 검수 기록을 읽어라. 서비스가 실행 가능하면 대표 사용자 흐름을 직접 확인하라.
2. 사용자 관점의 기능별로 페이지를 나누라. 개발 내부 구조를 매뉴얼 목차로 쓰지 마라.
3. 기능 설명은 구현 근거에 맞춰라. 미구현 기능은 제공 기능처럼 안내하지 말고 미구현으로 표시하라.
4. 실행 확인이 불가능하면 코드 기준으로 작성했음을 명시하고 해당 항목을 '실행 미확인'으로 표시하라. 테스트 결과를 꾸며내지 마라.
5. 재현에 필요한 URL·역할·사전 데이터와 앱 버전 또는 커밋을 가능한 범위에서 기록하라. 실제 계정 비밀번호·비밀키·개인정보를 넣지 마라.

## 번호와 페이지 규칙

- 고정 ID는 P01-01 형식을 사용하라. P01은 논리 페이지, 01은 그 페이지의 항목이다.
- 각 페이지 제목에 '1페이지 · 시작하기 (P01)', 항목 제목에 '1번 · 항목 등록 (P01-01)'처럼 번호와 ID를 함께 표시하라.
- 매뉴얼 표지·목차는 번호 없는 안내 영역으로 두고, 검수 페이지는 1페이지부터 시작하라. HTML의 스크롤 길이가 페이지 번호를 결정하지 않게 하라.
- 이미 공유한 페이지·항목은 중간 삽입·정렬 변경으로 재번호하지 마라. 새 페이지·항목은 새 ID로 추가하고 제거한 ID는 '제거됨'으로 남겨라. ID를 다른 기능에 재사용하지 마라.
- '3페이지 2번'은 P03-02로 해석하라. 논리 페이지와 PDF 실제 페이지가 다르면 대응표를 표시하라.
- 같은 번호가 중복되거나 버전 때문에 대상이 불명확하면 추측 수정하지 말고 대상 ID를 확인하라.

## 항목 구조

각 항목에 다음 내용을 사용자가 따라할 수 있는 말로 작성하라:

1. 항목 ID와 기능 이름
2. 시작 화면과 사전 조건
3. 사용 절차: 누를 버튼, 입력할 값, 이동 순서
4. 기대 결과와 관련된 오류·빈 상태
5. 사용자 확인: 미확인 / 정상 / 수정 요청
6. 에이전트 검증: 실행 확인 / 코드 확인 / 실행 미확인, 검증 근거

사용자 확인과 에이전트 검증을 구분하라. 자동 테스트가 통과해도 사용자의 확인을 '정상'으로 바꾸지 마라. 관련 요구사항 ID를 붙이고 별도 매핑표에 구현 파일·화면 경로를 기록하라. 기술 매핑은 일반 사용자 설명과 분리하라.

## 전달과 검수

- HTML은 자체 포함 가능한 스타일과 간단한 페이지 이동으로 만들고, 브라우저에서 읽을 수 있는 실제 경로나 주소를 제공하라.
- 인쇄 시 논리 페이지마다 새 페이지가 시작되게 하라. 한 논리 페이지가 넘치면 레이아웃을 줄이거나 새 고정 ID 페이지로 나누고, 가능하면 인쇄 화면을 확인하라. 검증하지 않은 PDF 페이지 수를 보장하지 마라.
- Markdown과 HTML의 ID·절차·기대 결과를 대조하라. 가능한 경우 민감 정보가 없는 실제 화면 캡처를 넣되 스크린샷 없이도 절차를 이해할 수 있게 하라.
- '3페이지 2번: 삭제 전 확인창을 추가해줘' 같은 피드백 예시를 제공하라. 문서만 요청받았다면 요청 범위를 지켜라.

## 번호로 수정 요청을 받으면

1. 기존 매뉴얼의 지정 ID와 관련 화면·파일·요구사항을 읽고 요청을 연결하라.
2. 대상이 명확하면 구현 수정 요청으로 처리하라. 사용자가 문구만 수정하라고 했으면 문서만 고쳐라.
3. 해당 동작을 재현하고 최소 범위를 수정하라. 원래 필수 요구사항과 충돌하면 먼저 확인하라.
4. 해당 항목과 영향받는 흐름을 실제로 검증하고 실패를 수정하라.
5. ID를 유지하면서 코드, Markdown·HTML 매뉴얼, 관련 PRD·작업 목록 중 실제 변경에 필요한 문서를 함께 갱신하라.
6. 사용자 상태는 '수정 요청 — 반영, 재확인 대기'로 기록하고, 수행한 검증을 별도 표시하라. 사용자 재확인 전에는 승인 완료로 처리하지 마라.
7. 문서의 변경 이력에 버전, ID, 수정 내용, 검증 결과를 짧게 기록하라. 업데이트한 문서 링크와 같은 번호로 재검수할 방법을 알려라.

## 완료 기준

초기 전달은 실제 기능을 따라갈 수 있는 번호 매뉴얼과 미확인 상태가 명시된 때다. 수정 반영은 코드·문서·관련 검증이 일치할 때다. 최종 사용자 승인과 에이전트의 구현 완료를 구분하라.
