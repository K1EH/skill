# Build

작동하는 필수 기능을 먼저 완성하고 실행 결과로 확인하라. 사용자의 언어로 짧게 진행 상황을 알리라.

## 첫 호출 시 채팅 입력 안내

- 이 세션에서 이 스킬을 처음 사용하거나 사용자가 사용법을 물으면, 본 작업 전에 목적·필요 입력과 아래 입력 예시를 채팅으로 짧게 안내하라. 저장소 문서 링크만 주고 끝내지 마라.
- 먼저 현재 요청과 아래 허용된 인계·산출물에서 입력을 확인하라. 이미 입력이 충분하면 '현재 [실제 파일/요구사항]으로 진행합니다. 다음 요청은 아래처럼 입력할 수 있습니다'라고 알리고 짧은 예시를 보여준 뒤 재입력을 기다리지 말고 요청한 작업을 진행하라.
- 부족한 입력이 있을 때만 필요한 항목을 표시한 예시를 제시하고 해당 입력을 받아라. 예시의 대괄호는 실제로 모르는 항목에만 남기고, 아는 경로·선택·시간은 채워라. 민감한 값은 안내 예시에 복사하지 마라.
- 반복 호출에서 같은 설명을 계속 출력하지 말고 작업에 집중하라. 입력 안내를 추가 승인 절차로 만들거나 질문 예산을 초기화하지 마라. 인터뷰·PRD의 필수 확인 질문은 기존 공동 질문 예산에 포함하라.

목적: PRD와 선택한 디자인을 바탕으로 구현하고 검증합니다.

필요 입력: 사용할 PRD/구체적인 명세와 프로젝트. 있으면 선택 디자인·현재 오류. 선택: 깊이·남은 시간.

입력 예시:

```text
$3-build
PRD: [docs/PRD.md 또는 명세]
디자인: [선택 기록 경로 / 기존 디자인 사용]
현재 프로젝트의 미완료 기능부터 구현하고 검증해줘.
표준 모드, 남은 시간 [분]으로 진행해줘.
```

## 새 세션 재개와 프로젝트 파일

1. 현재 프로젝트의 docs/WORKFLOW_STATE.md(공통 상태), docs/WORKFLOW_SETTINGS.md(깊이·시간), 아래 지정한 현재 단계 인계 파일이 있으면 먼저 읽어라. 새 세션이 이전 대화를 안다고 가정하지 마라.
2. 공통 상태는 현재 단계·확정 문서 경로와 버전·다음 작업·미해결 문제·인계 경로만 담는 짧은 색인으로 유지하라. 과거 대화나 초기 결정의 상세 내용을 복사하지 마라. 링크된 문서를 재귀적으로 전부 읽지 말고 아래 단계별 범위 안에서만 읽어라.
3. 인계는 탐색용 기록이다. 지정된 실제 산출물·현재 코드·파일 변경 상태와 대조하고 오래된 내용은 갱신하라. 대화로만 확정됐던 내용은 사용자 확인 사실과 함께 산출물에 기록하되 초안·가정·미정·폐기된 제안을 확정 요구사항으로 승격하지 마라.
4. 시작·새 세션 재개·작업 종료·중단 또는 사용자 선택 대기 시 현재 단계 인계를 저장하라. 이미 끝난 작업과 사용한 질문 수, 명시적 선택, 사용자 확인 여부를 보존하여 같은 작업·질문·승인을 반복하지 마라. 남은 시간을 새 세션마다 180분으로 초기화하지 마라.
5. 인계 파일에는 대상 단계, 상태(진행 중/선택 대기/완료/막힘), 참조 가능한 파일과 버전, 완료·남은 작업, 실제 실행 명령·검증과 미확인 사항, 다음 행동을 짧게 기록하라. 다음 단계 인계에는 그 단계가 읽어도 되는 확정 결과·경로만 전달하라. 원본 인터뷰·폐기 초안·세션 대화록을 복사하지 마라.
6. 파일은 스킬 저장소나 설치 폴더가 아닌 실제 서비스 프로젝트에 작성하라. 사용자 지정 경로와 기존 문서 관례를 우선하고 실제 사용 경로를 색인에 기록하라. 필요한 파일만 만들고 기존 사용자의 변경을 덮어쓰지 마라. 파일 도구가 없으면 파일명과 내용을 제공하여 사용자가 다음 세션에 넘길 수 있게 하라.
7. 인계가 없으면 허용된 현재 파일로 최소 인계를 복원하고 확인한 사실과 미확인을 구분하라. 필수 입력이 없거나 서로 충돌하여 진행을 결정할 수 없을 때만 해당 내용에 한해 질문하라. 세션을 바꾸는 것 자체를 필수 절차로 만들지 마라.

### 이 단계의 참조 범위와 전달

- 현재 인계: docs/handoffs/3-build.md.
- 입력: 문제 원문·실행/제출 조건, 최신 PRD, 선택된 디자인(해당 시), 현재 코드, docs/TASKS.md와 기존 검증 결과. 초기 인터뷰·폐기된 초안을 자동 참조하지 마라.
- docs/TASKS.md에 요구사항 ID별 완료·미완료·작업 중인 파일을 유지하고, docs/VERIFICATION.md에 실행 명령·결과·실패·미확인을 짧게 기록하라. 코드를 바꾼 뒤 기존 성공 결과가 여전히 유효한지 재확인하라.
- 중단 시 저장되지 않은 변경·알려진 오류·재현법·실행 명령·다음 우선순위를 현재 인계에 남겨라. 새 세션에서는 현재 코드를 대조하여 이미 완료된 구현을 반복하지 마라.
- 매뉴얼 검수로 넘길 때 docs/handoffs/5-manual-review.md를 작성하라. 최신 확정 PRD의 경로·버전·확인 상태, 실제 구현 위치·실행 방법, 검증 결과·미완료 항목, 기존 매뉴얼·피드백 경로, 화면 확인에 필요한 경우 선택된 디자인만 담아라.
- 5번 인계에는 초기 인터뷰 결정사항·대화·초안의 상세 내용과 그 내용을 읽으라는 지시를 넣지 마라. 확정되지 않은 PRD는 확정이라고 표시하지 말고 검수 기준 미확정 사실을 남겨라. 필수 기능 누락은 숨기지 마라.

## 진행 깊이 선택

- 빠르게(quick), 표준(standard), 깊게(deep) 중 사용자가 지정한 모드를 적용하라. 기본은 표준이다.
- 작업 프로젝트의 docs/WORKFLOW_SETTINGS.md가 있으면 읽고 모드·남은 시간·개별 설정을 재사용하라. 현재 사용자의 명시적 요청을 가장 우선하라.
- 모드가 없으면 표준을 적용한다고 한 줄 알리고 진행하라. 사용자가 먼저 선택하겠다고 요청하면 세 모드 중 선택을 받아라. 이미 정한 모드를 반복 질문하지 마라.
- 선택·변경된 값은 파일 도구가 있으면 docs/WORKFLOW_SETTINGS.md에 짧게 기록하라. 파일이 없으면 새로 만들되 기존 설정의 다른 항목은 보존하라. 파일 도구가 없으면 대화에 기록하라.
- 아래 숫자는 자연어 기본값과 목표 예산이다. 자동 타이머나 프로그램의 강제 제한이 아니다. 실제 남은 시간을 확인할 수 없으면 사용자에게 받은 시간을 사용하고 추정임을 표시하라.
- 깊이를 줄여도 원문 필수 기능, 고정 ID, 명시적인 시안 선택, 실제 검증의 정직성은 유지하라. 시간 부족 때문에 필수 기능을 조용히 제외하지 마라.

| 모드 | 계획·구현 방식 | 검증 범위 |
| --- | --- | --- |
| 빠르게 | 3~5개 작업으로 묶고 필수 흐름부터 구현 | 빌드·핵심 흐름·수정한 버그 재확인 |
| 표준 | 보통 4~8개 작업, 화면·데이터 경계를 먼저 확정 | 핵심 로직·저장·오류 상태·주요 UI 흐름 |
| 깊게 | 필요할 때 8~12개 작업, 위험한 계약과 상태를 더 명확히 | 주요 경계값·관련 회귀·화면 상태까지 추가 검증 |

어떤 모드도 모든 변경에 TDD나 복잡한 아키텍처를 강제하지 마라. 3시간 시험 표준 흐름에서는 구현·통합에 약 100~120분, 검증·매뉴얼·제출에 약 30분 이상을 목표로 남기되 실제 요구사항과 남은 시간에 맞춰 조정하라. 선택 기능을 추가하기 전에 필수 기능과 검증을 끝내라.

## 조정 가능한 기본값 — 표준 모드 기준

- 작업 목록: 보통 4~8개. 작업마다 목적, 관련 파일, 확인 방법만 기재.
- 문서: 기존 PRD·작업 목록·간결한 검증 기록과 단계 인계를 유지. 프로젝트 관례나 사용자 경로를 우선.
- 구현: 메인 에이전트가 진행. 독립적인 작업이 분명할 때만 4-delegate를 선택적으로 사용.
- 검토: 마지막에 통합 검토 1회. 모든 작업마다 별도 리뷰 에이전트를 만들지 마라.
- 시간 제한이 주어지면 마지막 약 20%를 통합·확인에 남겨라. 제한이 없으면 임의 마감을 만들지 마라.

## 1. 확인과 계획

1. 문제 설명, PRD, 기존 코드와 실행 명령을 읽어라. 명세의 필수 요구사항 ID를 작업과 연결하라.
2. 요구사항을 만족하는 가장 단순한 기존 구조를 활용하라. 프레임워크·의존성·추상화를 필요 없이 늘리지 마라.
3. 화면, 데이터, 저장 방식 등 경계를 정하고 첫 실행 가능한 사용자 흐름부터 순서를 잡아라. 선택된 디자인 기록이 있으면 후보 ID·버전, 토큰/컴포넌트 참조, 반응형 규칙, 사용자 수정 메모를 구현 기준으로 사용하라.
4. 이미 구현 요청을 받았으면 작업 목록을 작성한 뒤 구현을 계속하라. 단계마다 계속 여부를 재질문하지 마라.

## 2. 구현

- 필수 기능의 입력부터 결과까지 한 흐름을 먼저 연결하라. 이후 다른 필수 기능을 완성하라.
- 시안에서 선택한 정보 위계·배치·컴포넌트 상태를 실제 데이터에 연결하라. 디자인 수정 메모를 항목별로 확인하고 비교 사이트 전용 도구·샘플 데이터를 서비스 구현에 그대로 남기지 마라.
- 요구된 데이터 저장·오류 처리를 포함하라. 실제 연동을 임의로 가짜 데이터로 대체하지 마라.
- 사소한 미정 사항은 가정과 이유를 짧게 기록하고 진행하라. 필수 조건 충돌은 사용자에게 확인하라.
- 문제가 생기면 재현, 원인 확인, 최소 수정, 재확인 순으로 해결하라.
- 파일이나 공용 API를 여러 에이전트가 동시에 변경하지 않게 하라.
- 브랜치·worktree·배포·반복적인 커밋을 자동으로 강제하지 마라. 요청과 프로젝트 규칙을 따르라.
- 비밀키는 소스와 클라이언트 번들에 넣지 마라. 외부 입력과 요구된 권한을 필요한 범위에서 확인하라.

## 3. 검증

변경에 맞는 확인만 수행하라:

- 프로젝트의 빌드·타입 검사·린트 중 적용 가능한 명령.
- 핵심 계산, 데이터 변환, 상태 변경과 버그 재발을 잡는 테스트.
- 주요 사용자 흐름, 오류·빈 상태, 필요한 저장 및 새로고침 동작.
- UI를 변경했고 브라우저 도구가 있으면 실제 화면과 상호작용 확인.

모든 변경에 TDD를 강제하거나 구현을 그대로 복제하는 테스트를 만들지 마라. 실패한 검증을 수정하고 다시 실행하라. 도구가 없거나 시간이 부족하면 확인하지 못한 부분을 명시하라. 결과 없이 성공을 선언하지 마라.

## 4. 마무리

PRD의 필수 항목과 결과를 대조하고 작업 목록을 갱신하라. 구현한 기능, 실행 방법, 실제 수행한 검증, 남은 제한을 짧게 보고하라. 선택 기능은 필수 기능과 확인이 끝나고 시간이 남을 때만 추가하라.
