# 2. PRD

**게이트 G2: 사람이 PRD를 승인하기 전에는 아무것도 만들지 않는다.** 서비스 코드, 프로젝트 생성, 의존성 설치, 구현 스킬 호출이 모두 여기에 든다. 읽고 데이터를 세는 것은 괜찮다. 사람이 재촉해도 이 게이트는 건너뛰지 않는다.

`docs/DATA_PROFILE.md`, `docs/DECISIONS.md`, `docs/PRD.md`를 먼저 읽는다. 프로파일이 없으면 먼저 만든다(G1). 목표 시간은 전체의 10% 안팎이다.

## 1. 접근 방식 고르기

쓰기 전에 어떻게 만들지를 한 메시지로 보여준다. 대안을 여러 개 떠올린 뒤 과제 목적에 어긋나거나 데이터·제약이 배제하는 것을 지우고, 남은 2~3개를 각각 잃는 것과 함께 적는다. 하나를 추천하고 이유를 말한 뒤 고르게 한다. 합리적인 길이 하나뿐이면 그렇게 말하고 다른 길이 왜 안 맞는지 설명한다.

기술 스택은 과제가 지정한 것을 쓴다. 지정이 없으면 작업 공간에 설치된 런타임에서 가장 단순한 구성을 내가 정하고, 사람이 고른 것처럼 적지 않고 내 판단이라고 적는다.

## 2. PRD 쓰기

`docs/PRD.md`(kickoff에서 과제 지정 파일로 옮겼으면 그 파일)를 100줄 안팎으로 채운다. 이 과제를 처음 보는 개발자가 다시 묻지 않고 구현을 계획할 수 있으면 충분하다. 길게 쓰지 않는다.

- 목적과 이유, 목표, 제외 범위, 실패로 볼 결과
- 접근 방식: 검토한 대안, 잃는 것, 고른 것과 이유
- 기준 입력과 나머지 입력의 처리. 결정 ID를 근거로 단다.
- 입력 규칙과 잘못된 입력의 처리(거부, 제외, 수정). 원문이나 담당자 답을 근거로 달고, 근거가 없으면 담당자에게 묻는다.
- 핵심 결과의 판정 기준. 이 과제의 결과에 맞는 것을 고르고, 근거 없는 숫자를 쓰지 않는다.
  - 생성·배정 결과: 입력 수와 제약에서 산식으로 유도한 결과별 예상 범위. 예: 입력 N건, 항목당 용량 C면 최소 ⌈N/C⌉개. 상한은 극단값이 아니라 제약을 지키는 현실적인 값으로 잡고, 하한의 3배를 넘으면 좁히거나 왜 넓은지 적는다.
  - 규칙·상태 변화: 정상, 경계, 거부 사례마다 입력과 기대 결과를 적은 표
  - AI·비결정 결과: 고정 예시 입력과 코드로 판정할 수 있는 통과 조건, 목표 통과율
  - 기준을 세울 수 없으면 담당자 질문으로 돌린다.
- 숫자 완료 조건: 범위, 사례 통과 수, 통과율처럼 실행해서 판정할 수 있는 조건
- 멈춤 조건: 어떤 결과가 나오면 진행을 멈추고 알릴 것인가
- 요구사항 R마다 관찰 가능한 완료 조건
- 데이터 모델 핵심, 화면 목록

담당자가 말한 것만 담당자 답으로 적는다. 내가 채운 것은 내 판단으로 표시하고 이유를 단다.

## 3. 자체 점검

원문을 옆에 두고 직접 고친다.

1. 요구사항 누락: 원문의 문장마다 R이 있는가
2. 빈 문장: "TBD", "적절히 처리" 같이 아무것도 정하지 않은 문장이 있는가
3. 일관성: 같은 것을 다른 이름으로 부르거나 서로 모순되는 곳이 있는가
4. 비례: 원문보다 몇 배 길거나 구현 코드를 적고 있지 않은가

## 4. 별도 세션 검수

사람에게 `review` 탭의 별도 Codex 세션이나 서브에이전트에 보낼 요청문을 준다. 요청문은 과제 원문과 PRD, `docs/DECISIONS.md`만 읽고, 이 문서로 구현을 계획할 때 막히는 곳, 누락, 모순, 근거 없는 수치를 찾아 달라는 내용이다. 내 결론을 요청문에 넣지 않는다.

지적을 그대로 믿지 않는다. 원문이나 데이터로 직접 확인해 셋으로 나눈다.

- 이미 답이 있음: 문서에 답을 적는다.
- 사소함: 만드는 것이 달라지지 않으면 내가 정하고 내 판단으로 표시한다.
- 업무 규칙: 담당자에게 묻는다. 답을 받지 못하면 결정이 아니라 가정 표에 적는다.

요청 원문과 지적별 수용·수정·폐기, 판단 근거를 그 자리에서 `docs/AI_LOG.md`에 적는다. 검수로 기준을 고치는 것은 사람의 승인 전에 끝낸다.

## 5. 승인

검수 결과를 처리하기 전에는 승인을 요청하지 않는다. 사람에게 15줄 이내로 보여주고 OK를 한 번 받는다: 기준 입력, 핵심 결과 기준, 데이터 모델 핵심, 화면 목록, 제외한 것, 검수에서 받아들이거나 버린 것, 내가 정한 것. "좋아 보인다"는 말은 보여준 것에 대한 승인일 뿐이니, 아직 쓰지 않은 내용까지 승인으로 치지 않는다.

OK를 받으면 PRD의 G2 상태를 고치고 `prd: G2 승인, R·D ID` 형식으로 커밋한 뒤 `$3-core`를 안내한다. 승인 후 기준을 바꾸려면 근거를 D 항목으로 남기고 다시 OK를 받는다.
