# 4. Build

`scripts/check_core.*`을 실행해 통과를 확인한 뒤 시작한다. 통과하지 않으면 `$3-core`로 돌아간다. `docs/PRD.md`와 `docs/TASKS.md`를 읽고 다음 미완료 작업부터 이어간다. 사람이 남은 시간을 말하지 않았으면 한 줄로 묻는다. 오류는 `.agents/skills/3-core/SKILL.md`의 "디버깅" 절차를 따른다.

## 1. 저장, API, 사용자 흐름

- 필수 흐름 하나를 입력부터 결과까지 먼저 연결하고 나머지를 붙인다. 실제 데이터를 쓰고 목업으로 대체하지 않는다.
- 서버 규칙은 AGENTS.md를 따른다. Vite는 `server.allowedHosts: true`, Next.js는 `allowedDevOrigins`처럼 프록시 호스트를 막는 설정이 있는지 확인한다.
- API는 `curl`로 검증하고 결과를 `docs/TASKS.md`에 짧게 적는다.
- 핵심 로직을 바꿨으면 `check_core`을 다시 실행한다.

## 2. 변경·경계 시나리오

요구사항이 말하지 않았다고 해서 그 입력에 프로그램이 깨져도 되는 것은 아니다. 사용자에게 가장 먼저 문제가 될 입력을 3~5개 골라 `scripts/check_scenarios.*`로 실제로 돌리고 `docs/TASKS.md`의 "시나리오 결과"에 적는다. 추측으로 적지 않는다. 원본 데이터는 바꾸지 않고 복사본이나 필터로 실행한다.

- 입력 값이 바뀔 때: 필터, 상태 값, 관리자가 수정한 결과가 재생성에서 어떻게 되는가
- 규칙을 만족할 수 없을 때: 용량 상한을 넘는 입력
- 대상이 없을 때: 입력 0건
- 입력이 커질 때: 2배, 10배에서 실행 시간과 결과 수

오류로 죽거나 조용히 틀린 결과를 내면 고치거나, 시간이 없으면 "깨지기 쉬운 곳"으로 기록한다.

## 3. 화면

시안을 여러 개 만들지 않는다. 코드 전에 짧은 계획을 세우고, 대조하고, 실데이터로 확인한다.

**계획 (15줄 이내, 대화로 보여준 뒤 바로 진행, 건너뛰지 않음):**

- 화면마다 "누가 무엇을 판단하려고 보는가" 한 줄. 과제의 업무 맥락에서 출발한다.
- ASCII 와이어프레임과 정렬 방향
- 색 4~6개(이름과 hex), 글꼴과 역할, 간격 토큰

그다음 과제 원문과 대조한다. 빠진 필수 항목을 고치고, 어느 과제에나 쓸 수 있는 기본값처럼 보이는 부분을 이 과제에 맞게 바꾼 뒤 구현한다.

**정보 구조:**

화면 형태는 업무에 맞춘다. 대화나 입력 중심 화면이면 아래 목록 규칙 중 해당하는 것만 적용한다.

- 첫 화면은 요약 수치와 판단에 필요한 것을 보여준다. 전체 목록을 쏟아내지 않는다.
- 항목이 50개를 넘는 목록은 기본을 그룹·요약으로 두고 검색, 필터, 페이지 이동을 붙인다.
- 지도, 차트처럼 표시량이 많은 요소도 기본 표시를 선택 항목이나 상위 항목으로 줄인다.
- 일반 사용자 화면은 자기 것만 보여주고 관리자 화면과 분리한다.
- 화면마다 주요 행동은 하나다.

**시각과 문구:**

- 선, 번호, 라벨 같은 장치는 정보를 담을 때만 쓴다. 똑같은 둥근 카드와 그림자를 반복하는 기본 틀을 피한다.
- 사용자 동작에 답하지 않는 움직임은 넣지 않는다. 힘을 줄 곳은 한 군데로 하고, 나머지는 절제한다. 끝나기 전에 장식 하나를 뺀다.
- 기본 품질: 모바일 폭 대응, 키보드 포커스 표시, 충분한 대비.
- 내부 구조가 아니라 담당자가 쓰는 업무 용어로 쓴다. 버튼은 실제 동작 이름으로 쓰고, 그 이름을 결과 메시지까지 유지한다.
- 오류는 무엇이 잘못됐고 어떻게 고치는지 말한다. 빈 화면은 다음 행동을 안내한다.

**전체 실데이터로 확인한다.** 샘플 몇 건으로 보기 좋은 것은 통과가 아니다. 스크린샷 도구가 이미 있거나 빠르게 설치되면 직접 보고 고친다. 아니면 사람에게 PORT, 경로, 볼 것을 알려주고 Browser에서 확인을 받는다. 화면을 실제로 열어 보기 전에는 완료라고 하지 않고 미확인으로 보고한다.

## 4. 서브에이전트 위임

세션당 최대 2개(메인 제외)이며 요청해야 생성된다. 공용 계약이 정해진 뒤, 서로 독립된 작업에만 쓴다. 2개가 이미 실행 중이면 끝나기를 기다리거나 메인이 직접 한다.

- 적합: 서로 다른 파일의 화면, 테스트 작성, 요구사항 누락 검토
- 부적합: 설계, 핵심 로직, 하나를 고치면 다른 것도 풀릴 수 있는 관련 문제, 전체 맥락이 있어야 이해되는 문제, 같은 파일을 건드리는 작업

프롬프트는 집중되고, 그것만 읽어도 이해되고, 출력이 구체적이어야 한다.

- 범위: 수정 가능한 파일 하나의 문제 영역. "전부 고쳐"가 아니라 대상을 지정한다.
- 맥락: 오류 메시지와 공용 계약을 직접 붙여 준다. 대화를 안다고 가정하지 않는다.
- 제약: 건드리지 말 것을 적는다.
- 기대 출력: 찾은 것, 변경 파일, 실행한 명령과 결과

모델은 복잡한 작업에 `gpt-6.1-sol`, 좁고 빠른 작업에 `gpt-6-luna`를 쓰되 환경에서 제공될 때만 지정한다.

돌아오면 요약을 읽고, 같은 코드를 건드렸는지 `git status`와 `git diff`로 확인하고, 전체 검증을 직접 실행한다. 에이전트의 성공 보고는 증거가 아니다. "수정하지 말라"는 지시도 샌드박스가 아니다.

## 5. 마무리

필수 R이 모두 구현되면 G4에 따라 실행 결과를 확인하고 커밋한 뒤 `$5-finish`를 안내한다. 선택 기능은 필수와 검증이 끝나고 시간이 남을 때만 한다.
