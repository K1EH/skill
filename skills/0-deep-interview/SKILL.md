# Deep Interview

요구사항의 숨은 가정과 정책·예외를 선택 가능한 설계 결정으로 바꾸고, 사용자 선택을 실행 가능한 명세로 정리하라. 질문의 수보다 결정의 품질을 우선하고 답변은 사용자의 언어로 작성하라.

## 첫 호출 시 채팅 입력 안내

- 이 세션에서 이 스킬을 처음 사용하거나 사용자가 사용법을 물으면, 본 작업 전에 목적·필요 입력과 아래 입력 예시를 채팅으로 짧게 안내하라. 저장소 문서 링크만 주고 끝내지 마라.
- 먼저 현재 요청과 아래 허용된 인계·산출물에서 입력을 확인하라. 이미 입력이 충분하면 '현재 [실제 파일/요구사항]으로 진행합니다. 다음 요청은 아래처럼 입력할 수 있습니다'라고 알리고 짧은 예시를 보여준 뒤 재입력을 기다리지 말고 요청한 작업을 진행하라.
- 부족한 입력이 있을 때만 필요한 항목을 표시한 예시를 제시하고 해당 입력을 받아라. 예시의 대괄호는 실제로 모르는 항목에만 남기고, 아는 경로·선택·시간은 채워라. 민감한 값은 안내 예시에 복사하지 마라.
- 반복 호출에서 같은 설명을 계속 출력하지 말고 작업에 집중하라. 입력 안내를 추가 승인 절차로 만들거나 질문 예산을 초기화하지 마라. 인터뷰·PRD의 필수 확인 질문은 기존 공동 질문 예산에 포함하라.

목적: 요구사항의 중요한 설계 결정을 선택지와 근거로 확인하고 실행 가능한 명세로 정리합니다.

필요 입력: 문제 원문 또는 자료 경로, 이미 정한 제약. 선택: 깊이·질문 수·남은 시간.

입력 예시:

```text
$0-deep-interview
[만들 서비스 또는 시험 요구사항 원문/파일 경로]
표준 모드, 질문 최대 6개로 중요한 결정과 주요 예외를 확인해줘.
이미 정한 제약: [기술/기한 또는 없음]
```

## 새 세션 재개와 프로젝트 파일

1. 현재 프로젝트의 docs/WORKFLOW_STATE.md(공통 상태), docs/WORKFLOW_SETTINGS.md(깊이·시간), 아래 지정한 현재 단계 인계 파일이 있으면 먼저 읽어라. 새 세션이 이전 대화를 안다고 가정하지 마라.
2. 공통 상태는 현재 단계·확정 문서 경로와 버전·다음 작업·미해결 문제·인계 경로만 담는 짧은 색인으로 유지하라. 과거 대화나 초기 결정의 상세 내용을 복사하지 마라. 링크된 문서를 재귀적으로 전부 읽지 말고 아래 단계별 범위 안에서만 읽어라.
3. 인계는 탐색용 기록이다. 지정된 실제 산출물·현재 코드·파일 변경 상태와 대조하고 오래된 내용은 갱신하라. 대화로만 확정됐던 내용은 사용자 확인 사실과 함께 산출물에 기록하되 초안·가정·미정·폐기된 제안을 확정 요구사항으로 승격하지 마라.
4. 시작·새 세션 재개·작업 종료·중단 또는 사용자 선택 대기 시 현재 단계 인계를 저장하라. 이미 끝난 작업과 사용한 질문 수, 명시적 선택, 사용자 확인 여부를 보존하여 같은 작업·질문·승인을 반복하지 마라. 남은 시간을 새 세션마다 180분으로 초기화하지 마라.
5. 인계 파일에는 대상 단계, 상태(진행 중/선택 대기/완료/막힘), 참조 가능한 파일과 버전, 완료·남은 작업, 실제 실행 명령·검증과 미확인 사항, 다음 행동을 짧게 기록하라. 다음 단계 인계에는 그 단계가 읽어도 되는 확정 결과·경로만 전달하라. 원본 인터뷰·폐기 초안·세션 대화록을 복사하지 마라.
6. 파일은 스킬 저장소나 설치 폴더가 아닌 실제 서비스 프로젝트에 작성하라. 사용자 지정 경로와 기존 문서 관례를 우선하고 실제 사용 경로를 색인에 기록하라. 필요한 파일만 만들고 기존 사용자의 변경을 덮어쓰지 마라. 파일 도구가 없으면 파일명과 내용을 제공하여 사용자가 다음 세션에 넘길 수 있게 하라.
7. 인계가 없으면 허용된 현재 파일로 최소 인계를 복원하고 확인한 사실과 미확인을 구분하라. 필수 입력이 없거나 서로 충돌하여 진행을 결정할 수 없을 때만 해당 내용에 한해 질문하라. 세션을 바꾸는 것 자체를 필수 절차로 만들지 마라.

### 이 단계의 참조 범위와 전달

- 현재 인계: docs/handoffs/0-deep-interview.md.
- 입력: 사용자가 제공한 문제 원문·자료, 관련 현재 코드, 기존 인터뷰 결정사항. 이미 확정 PRD가 있는 수정 작업은 해당 PRD의 유효한 내용을 보존하라.
- 결과를 docs/REQUIREMENTS_DECISIONS.md에 저장하라. 확정 사항(사용자 확인 근거), 제외 범위, 가정, 열린 질문을 구분하고 질문 예산·사용한 질문 수·답변으로 결정된 내용만 짧게 기록하라. 전체 인터뷰 대화록은 필요하지 않다.
- 사용자 답변을 기다릴 때도 현재 인계와 질문 사용량을 저장하라. 재개하면 미응답 질문부터 이어가라.
- 1-prd로 넘길 때 docs/handoffs/1-prd.md에 문제 원문 경로, 결정사항 파일, 남은 질문 예산과 미정 사항을 기록하라. 이 결과를 최종 승인된 PRD인 것처럼 표시하지 마라.

## 진행 깊이 선택

- 빠르게(quick), 표준(standard), 깊게(deep) 중 사용자가 지정한 모드를 적용하라. 기본은 표준이다.
- 작업 프로젝트의 docs/WORKFLOW_SETTINGS.md가 있으면 읽고 모드·남은 시간·개별 설정을 재사용하라. 현재 사용자의 명시적 요청을 가장 우선하라.
- 모드가 없으면 표준을 적용한다고 한 줄 알리고 진행하라. 사용자가 먼저 선택하겠다고 요청하면 세 모드 중 선택을 받아라. 이미 정한 모드를 반복 질문하지 마라.
- 선택·변경된 값은 파일 도구가 있으면 docs/WORKFLOW_SETTINGS.md에 짧게 기록하라. 파일이 없으면 새로 만들되 기존 설정의 다른 항목은 보존하라. 파일 도구가 없으면 대화에 기록하라.
- 아래 숫자는 자연어 기본값과 목표 예산이다. 자동 타이머나 프로그램의 강제 제한이 아니다. 실제 남은 시간을 확인할 수 없으면 사용자에게 받은 시간을 사용하고 추정임을 표시하라.
- 깊이를 줄여도 원문 필수 기능, 고정 ID, 명시적인 시안 선택, 실제 검증의 정직성은 유지하라. 시간 부족 때문에 필수 기능을 조용히 제외하지 마라.

| 모드 | 질문 예산 | 탐색 범위 | 3시간 시험의 목표 시간 |
| --- | --- | --- | --- |
| 빠르게 | 최대 2개 | 가장 영향이 큰 미정 정책·완료 기준 | 3~5분 |
| 표준 | 최대 6개 | 사용자 흐름·정책·상태·예외·완료 기준의 핵심 결정 | 10~15분 |
| 깊게 | 최대 12개 | 숨은 가정·반례·정책 충돌·데이터 수명·대안의 비용까지 | 20~30분 |

질문은 한 번에 하나씩 하고 이미 명확하면 예산을 채우지 말고 종료하라. 질문 예산은 1-prd와 합산하라. 깊게 모드는 장기 운영·사업·보안 인터뷰를 자동 추가하는 뜻이 아니다. 사용자가 '질문 최대 5개'처럼 지정하면 그 값을 우선하라.

## 조정 가능한 기본값 — 표준 모드 기준

- 질문 예산: 표준은 현재 요구사항 정리 과정 전체에서 최대 6개. 다른 모드는 위 표를 적용.
- 진행 방식: 한 번에 하나의 설계 결정. 결정이 필요한 질문은 실질적인 선택지 2~3개와 자유 입력, 각 선택의 장단점·추천 이유를 제공.
- 결과 분량: 표준은 보통 60줄 안팎, 깊게는 필요한 결정·예외를 빠뜨리지 않는 간결한 명세. 대화록 전체를 복사하지 마라.
- 사용자 설정을 이 기본값보다 우선하라. 이미 답한 질문은 예산에서 다시 시작하지 마라.

## 심층 질문의 기준

다음 축을 참고하되 체크리스트를 모두 질문하지 말고 현재 프로젝트에서 영향이 큰 미정 사항부터 골라라.

- 사용자·상황: 누가 어떤 순간에 어떤 결과를 얻어야 하는가. '관리하기 편하게'처럼 추상적이면 성공 사례 하나로 구체화하라.
- 업무 정책: 등록·수정·삭제·취소·완료·기한 초과 시 허용하는 행동과 우선순위. 화면 이름만 정하고 정책을 건너뛰지 마라.
- 상태와 예외: 빈 값·중복·실패·만료·이미 처리된 항목에서 기대하는 결과. 관련될 때만 역할 차이·동시 수정·복구를 다루라.
- 데이터 수명: 새로고침·재접속·삭제·가져오기 이후 무엇이 남아야 하는가. 날짜·시간대·단위의 경계가 동작을 바꾸면 확인하라.
- 범위·상충: 사용자가 요구한 두 조건이 충돌하거나 시간 제약 때문에 대안이 갈리는 지점을 찾아라. 명시된 필수 기능은 임의로 선택 사항으로 바꾸지 마라.
- 완료 판정: 선택한 정책을 어떤 입력·행동·결과로 검증할 것인가. 테스트할 수 없는 표현은 관찰 가능한 조건으로 바꾸라.

## 선택형 질문 진행

1. 원문·현재 코드·기존 결정 파일을 먼저 읽고 명시된 사실과 미정 사항을 구분하라. 코드나 자료로 알 수 있는 내용을 사용자에게 묻지 마라.
2. 영향 범위가 크고 불확실하며 나중에 바꾸기 어려운 결정을 먼저 골라라. 확인된 모순이나 중요한 누락이 있으면 이유를 한 문장으로 밝히라.
3. 결정이 필요한 질문은 아래 형식으로 제시하고 답변을 기다려라. 선택지마다 사용자 행동·정확성·구현 비용 중 실제 차이가 나는 점을 적어라. 장점만 나열하거나 사실상 같은 선택지를 만들지 마라.
4. 추천안은 제약과 근거를 밝혀 제안하되 사용자가 선택한 것으로 취급하지 마라. 모든 선택지는 원문 필수 요구사항을 만족해야 한다. 가능한 선택지가 없으면 충돌을 설명하고 필요한 변경을 확인하라.
5. 답을 받으면 선택한 정책과 이유를 기록하고 적용될 완료 조건 또는 짧은 예시를 정리하라. 새로운 중요한 예외가 드러났을 때만 다음 질문을 그 결정에 연결하라.
6. 깊게 모드에서는 영향이 큰 선택에 반례·경계 상황을 하나 적용하여 요구사항 충돌을 확인하라. 이미 답한 내용을 다른 말로 재질문하거나 모든 결정에 추가 승인을 요구하지 마라.
7. 정보 자체를 알아야 선택지를 만들 수 없다면 그 사실 하나를 먼저 질문할 수 있다. 선택지를 만들기 위해 불필요한 기능·정책 결정을 추가하지 마라.
8. 미정 핵심 사항이 해소되고 주요 정책·예외·완료 기준이 정리되면 예산을 채우지 말고 종료하라. 예산이 끝나면 열린 질문과 영향을 표시하고 비핵심은 가정으로 남겨라. 해결되지 않은 필수 조건 충돌은 숨기지 마라.

질문 형식:

```text
결정할 사항: [지금 정할 하나의 정책]
왜 중요한가: [사용 흐름이나 구현·검증에 미치는 영향 한 문장]
A. [방식] — [이점] / [제약·비용]
B. [방식] — [이점] / [제약·비용]
C. [필요할 때만 다른 실질적 방식]
추천: [선택지와 현재 요구사항에 근거한 이유]
답변: A/B/C 또는 원하는 정책을 직접 설명해주세요.
```

한 메시지에 여러 결정을 몰아넣지 마라. 질문 하나는 별도로 판단할 설계 결정 하나를 뜻하며, 답변을 확인했다는 표시만으로 질문 수를 늘리지 마라. 사용자 답변에 선택과 추가 조건이 함께 있으면 둘 다 반영하라.

질문 수준 예시 — 원문에서 '마감일'의 의미가 미정인 과제 서비스:

```text
결정할 사항: 마감일이 지난 과제도 완료 처리할 수 있나요?
왜 중요한가: 완료 버튼의 동작과 지연 과제 집계 기준이 달라집니다.
A. 허용하고 '지연 완료'로 구분 — 실제 수행 기록 유지 / 상태 구분 추가
B. 완료 처리를 막음 — 엄격한 마감 정책 / 뒤늦게 수행한 기록을 남기기 어려움
추천: 개인 과제 관리라면 A, 마감 준수가 핵심인 평가 서비스라면 B가 적합합니다.
답변: A/B 또는 다른 정책을 알려주세요.
```

이 예시는 질문 형식 설명일 뿐 실제 프로젝트의 정책으로 복사하지 마라. 선택 후에는 '지연된 항목의 완료 처리 시 기대 결과'처럼 검증 조건까지 기록하라.

## 결과

다음 항목을 간결하게 정리하라:

- 목표와 사용자
- 반드시 구현할 기능
- 이번에 제외할 기능
- 시간·기술·데이터 제약
- 관찰 가능한 완료 기준
- 중요 결정별 선택지·사용자 선택·선택 이유
- 확정된 정책과 관련된 주요 예외·상태 전환
- 가정과 남은 질문

확정 결정은 D1, D2 같은 ID를 붙이고 선택·근거·관련 완료 조건을 연결하라. 1-prd에는 전체 인터뷰 대화가 아니라 확정 결정과 미정 사항을 구분한 결과를 넘겨라.

PRD 요청이 있으면 이 결과를 1-prd의 입력으로 넘겨라. 인터뷰만 요청받았다면 여기서 끝내라. 구현은 구현 요청이 있을 때 진행하라.

## 범위

긴 점수 계산, 상태 관리용 JSON, 사업 전략 인터뷰는 기본으로 생성하지 마라. 인증·권한 등 요구된 조건은 보존하되 별도 보안 설계 문서를 자동 생성하지 마라.
