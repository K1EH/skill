# 5. Finish

새 기능을 만들지 않는다. 사람이 남은 시간을 말하지 않았으면 한 줄로 묻는다. 시간이 부족하면 2, 4, 5번을 먼저 끝낸다. 제출 버튼은 사람이 누른다.

## 1. 증거 규칙 (G4)

**새로 확인한 증거 없이 완료를 말하지 않는다.** 이번 메시지에서 검증 명령을 실행하지 않았다면 통과했다고 말할 수 없다. 규칙의 표현만 피해 가는 것도 위반이다.

어떤 상태를 주장하기 전에:

1. 찾기: 이 주장을 증명하는 명령은 무엇인가
2. 실행: 명령 전체를 새로 실행한다
3. 읽기: 출력 전체와 종료 코드, 실패 수를 읽는다
4. 확인: 출력이 주장을 뒷받침하는가. 아니면 실제 상태를 증거와 함께 말한다
5. 그다음에만 증거와 함께 주장한다

| 주장 | 필요한 것 | 충분하지 않은 것 |
| --- | --- | --- |
| 테스트 통과 | 테스트 출력: 실패 0 | 이전 실행, "통과할 것이다" |
| 빌드 성공 | 빌드 명령 종료 코드 0 | 린트 통과, 로그가 괜찮아 보임 |
| 버그 수정 | 원래 증상 재현 명령 통과 | 코드를 바꿨음 |
| 규모 정상 | `check_scale` 출력 전부 PASS | 샘플 몇 건이 맞음 |
| 에이전트 완료 | diff에 변경이 있고 직접 실행함 | 에이전트의 성공 보고 |
| 요구사항 충족 | 항목별 대조 | 테스트 통과 |

멈춰야 하는 신호: "아마", "될 것이다", "~인 듯"이라는 말, 확인 전에 "완료했습니다"라고 말하고 싶을 때, 커밋하려는데 검증을 안 했을 때, 에이전트 보고를 믿을 때, 일부만 확인했을 때, "이번만"이라는 생각. 지쳤거나 시간이 없어도 예외는 없다.

## 2. 원문 대조

과제 원문을 **다시 읽는다.** `docs/PRD.md`만 보지 않는다. 먼저 고치지 말고 찾은 것을 표로 정리한다. 없는 것을 있다고 지어내지 않는다.

- 커버리지: 원문·R 중 구현이나 작업이 없는 것, R 없는 구현
- 모호함: 수치 없는 형용사, TODO 같은 자리표시자가 남은 곳
- 명세 부족: 완료 조건이 관찰되지 않는 R
- 불일치: 결정(D)이 반영되지 않은 곳, 담당자 용어와 다른 용어, 문서 사이에 다른 수치
- 중복: 같은 요구를 두 번 적어 어긋날 수 있는 곳

빠진 요구사항은 R을 추가한다. `docs/TASKS.md`의 요구사항별 검증 표에 구현 위치, 실행한 검증과 결과, 상태(통과·실패·미확인)를 채운다. 실행하지 않은 것은 미확인이다. 문제가 없으면 없다고 수치와 함께 보고한다.

**제출 문서의 주장을 점검한다.** 문장마다 파일, 실행 결과, 커밋 중 하나로 뒷받침되는지 확인하고, 근거가 없거나 실제로 하지 않은 일이면 문서를 고친다.

심각도 순으로 고친다.

- 치명: 필수 기능 없음, 실행 불가, 제출 경로 틀림, G3 실패
- 높음: 필수 기능의 주요 예외 실패, 서로 충돌하는 요구, 검증할 수 없는 완료 조건
- 낮음: 나머지. 시간이 남을 때만 고친다.

## 3. 처음부터 실행

- 문서에 적은 실행 명령 그대로 다시 실행한다. 서버 재시작은 사람에게 요청한다.
- `scripts/check_scale.*`과 `scripts/check_scenarios.*`를 다시 실행하고 핵심 API를 `curl`로 확인한다.
- 사람용 검수 목록을 8개 이내로 준다: PORT와 경로, 누를 것, 기대 결과. 역할별 핵심 흐름을 포함한다. 사람의 답을 받기 전에는 사람 확인 완료로 적지 않는다.

## 4. 제출물

- 과제가 요구한 문서(PRD, 계획, 협업 기록 등)가 지정된 이름과 경로에 있는지 확인한다. 없는 내용을 꾸미지 않는다.
- 필수 파일의 경로와 이름을 `ls`로 확인한다. 실행 방법이 문서에 있는지 확인한다.
- 디버그 코드, 임시 파일, 키·토큰, 필요 없는 대용량 파일이 없는지 확인한다.
- `finish: 제출 준비` 형식으로 커밋한다.

## 5. 서술형 대비 요약

`docs/BRIEF.md`를 두 페이지 이내로 쓴다. 후속 서술형은 제출물과 작업 기록을 바탕으로 출제되고 AI를 쓸 수 없으므로, 사람이 직접 읽고 자기 말로 설명하기 위한 문서다. 파일, 실행 결과, `git log`에 있는 사실만 쓰고, 모르는 것은 모른다고 쓴다. 모범 답안은 쓰지 않는다. 다른 문서에 있는 표는 옮겨 적지 말고 핵심과 위치만 적는다.

1. 구조: 입력부터 화면까지 구성 요소별 입력, 출력, 역할, 파일 위치
2. 확인한 것과 추정한 것: 표로 구분하고, 다시 확인할 파일과 명령을 함께 적는다
3. 핵심 결정: D 항목별 선택, 근거, 버린 대안, 담당자 답
4. 시나리오: 실제로 돌린 결과와 약한 곳
5. 결과 검사 방법: 별도 코드 검사, 기준안 비교 수치, 입력이 커질 때의 병목
6. AI 협업: 요청 원문, 수용·수정·폐기와 각각의 근거
7. 실수와 수정: 무엇이 틀렸고 어떻게 알았고 어떻게 고쳤나
8. 제출 문서에 적힌 주요 주장과 근거 위치

시간이 부족하면 1, 2, 6번만 쓴다.

## 6. 사람에게 넘기기

아래를 그대로 안내한다.

1. `docs/BRIEF.md`를 직접 읽는다. 확정 후에는 다시 볼 수 없다고 가정한다.
2. 에디터의 저장 상태가 "저장됨"인지 확인한다.
3. "제출하고 문제풀기"로 미리보기를 연다. 미리보기 목록은 일부만 보일 수 있다.
4. "제출물 확정하고 문제풀기"를 누른다. 확정 후에는 수정할 수 없다.
5. 서술형은 질문의 전제가 실제 구현과 다르면 차이를 밝히고 자기 말로 답한다.
6. 완료 화면에서 제출 ID, 시각, 파일 수, 크기를 확인한다.
