# Frontend Preview

화면 목적과 사용자 행동에 근거한 디자인 방향을 먼저 정하고, 실제 제품처럼 읽히고 조작되는 UI 시안을 비교 페이지로 제공하라. 사용자가 명시적으로 선택한 디자인을 재현 가능한 구현 기준으로 기록하라. 답변과 화면 문구는 사용자의 언어를 따르라.

## 첫 호출 시 채팅 입력 안내

- 이 세션에서 이 스킬을 처음 사용하거나 사용자가 사용법을 물으면, 본 작업 전에 목적·필요 입력과 아래 입력 예시를 채팅으로 짧게 안내하라. 저장소 문서 링크만 주고 끝내지 마라.
- 먼저 현재 요청과 아래 허용된 인계·산출물에서 입력을 확인하라. 이미 입력이 충분하면 '현재 [실제 파일/요구사항]으로 진행합니다. 다음 요청은 아래처럼 입력할 수 있습니다'라고 알리고 짧은 예시를 보여준 뒤 재입력을 기다리지 말고 요청한 작업을 진행하라.
- 부족한 입력이 있을 때만 필요한 항목을 표시한 예시를 제시하고 해당 입력을 받아라. 예시의 대괄호는 실제로 모르는 항목에만 남기고, 아는 경로·선택·시간은 채워라. 민감한 값은 안내 예시에 복사하지 마라.
- 반복 호출에서 같은 설명을 계속 출력하지 말고 작업에 집중하라. 입력 안내를 추가 승인 절차로 만들거나 질문 예산을 초기화하지 마라. 인터뷰·PRD의 필수 확인 질문은 기존 공동 질문 예산에 포함하라.

목적: 정보 구조·시각 체계·핵심 상호작용이 다른 실제 UI 후보를 비교하고 선택한 방향을 구현 기준으로 확정합니다.

필요 입력: 최신 PRD 또는 화면 요구사항, 핵심 사용자·대표 흐름. 선택: 참고 화면·브랜드·기존 자산, 시안 수·깊이·시간 예산.

입력 예시:

```text
$2-frontend-preview
PRD: [docs/PRD.md 또는 실제 경로]
대표 흐름: [예: 목록에서 항목 확인 → 상세 열기 → 상태 변경]
표준 모드로 정보 구조와 시각적 방향이 다른 시안 3개를 만들어줘.
같은 데이터·핵심 행동으로 비교하고 모바일·빈 상태·오류 상태도 보여줘.
내가 선택하기 전에는 서비스 전체 구현을 시작하지 마.
```

## 새 세션 재개와 프로젝트 파일

1. 현재 프로젝트의 docs/WORKFLOW_STATE.md(공통 상태), docs/WORKFLOW_SETTINGS.md(깊이·시간), 아래 지정한 현재 단계 인계 파일이 있으면 먼저 읽어라. 새 세션이 이전 대화를 안다고 가정하지 마라.
2. 공통 상태는 현재 단계·확정 문서 경로와 버전·다음 작업·미해결 문제·인계 경로만 담는 짧은 색인으로 유지하라. 과거 대화나 초기 결정의 상세 내용을 복사하지 마라. 링크된 문서를 재귀적으로 전부 읽지 말고 아래 단계별 범위 안에서만 읽어라.
3. 인계는 탐색용 기록이다. 지정된 실제 산출물·현재 코드·파일 변경 상태와 대조하고 오래된 내용은 갱신하라. 대화로만 확정됐던 내용은 사용자 확인 사실과 함께 산출물에 기록하되 초안·가정·미정·폐기된 제안을 확정 요구사항으로 승격하지 마라.
4. 시작·새 세션 재개·작업 종료·중단 또는 사용자 선택 대기 시 현재 단계 인계를 저장하라. 이미 끝난 작업과 사용한 질문 수, 명시적 선택, 사용자 확인 여부를 보존하여 같은 작업·질문·승인을 반복하지 마라. 남은 시간을 새 세션마다 180분으로 초기화하지 마라.
5. 인계 파일에는 대상 단계, 상태(진행 중/선택 대기/완료/막힘), 참조 가능한 파일과 버전, 완료·남은 작업, 실제 실행 명령·검증과 미확인 사항, 다음 행동을 짧게 기록하라. 다음 단계 인계에는 그 단계가 읽어도 되는 확정 결과·경로만 전달하라. 원본 인터뷰·폐기 초안·세션 대화록을 복사하지 마라.
6. 파일은 스킬 저장소나 설치 폴더가 아닌 실제 서비스 프로젝트에 작성하라. 사용자 지정 경로와 기존 문서 관례를 우선하고 실제 사용 경로를 색인에 기록하라. 필요한 파일만 만들고 기존 사용자의 변경을 덮어쓰지 마라. 파일 도구가 없으면 파일명과 내용을 제공하여 사용자가 다음 세션에 넘길 수 있게 하라.
7. 인계가 없으면 허용된 현재 파일로 최소 인계를 복원하고 확인한 사실과 미확인을 구분하라. 필수 입력이 없거나 서로 충돌하여 진행을 결정할 수 없을 때만 해당 내용에 한해 질문하라. 세션을 바꾸는 것 자체를 필수 절차로 만들지 마라.

### 이 단계의 참조 범위와 전달

- 현재 인계: docs/handoffs/2-frontend-preview.md.
- 입력: 최신 PRD, 기존 디자인 시스템·화면·자산, docs/DESIGN_BRIEF.md와 이미 있는 docs/DESIGN_SELECTION.md. 초기 인터뷰나 폐기된 PRD 초안을 자동으로 열지 마라.
- 시안 비교 페이지 경로·실행 방법, 고정 후보 ID·개정 버전, 비교한 화면·상태·핵심 흐름, 실제 확인한 동작, 사용자 선택 대기 여부를 현재 인계에 기록하라. 재개했을 때 선택 대기라면 같은 시안을 무조건 새로 만들지 말고 기존 결과를 제시하라.
- 사용자가 선택한 뒤 docs/DESIGN_SELECTION.md에 후보 ID·개정 버전·수정 메모·적용 범위·명시적 선택 근거와 아래 구현 계약을 저장하라. 미선택 또는 기본 선택을 확정 선택으로 기록하지 마라.
- docs/handoffs/3-build.md에는 PRD와 선택 결과의 경로·버전, 구현 시 유지할 디자인 규칙과 다음 행동을 기록하라. 선택 전에는 인계를 '선택 대기'로 남기고 구현 단계 완료로 처리하지 마라.

## 진행 깊이 선택

- 빠르게(quick), 표준(standard), 깊게(deep) 중 사용자가 지정한 모드를 적용하라. 기본은 표준이다.
- 작업 프로젝트의 docs/WORKFLOW_SETTINGS.md가 있으면 읽고 모드·남은 시간·개별 설정을 재사용하라. 현재 사용자의 명시적 요청을 가장 우선하라.
- 모드가 없으면 표준을 적용한다고 한 줄 알리고 진행하라. 사용자가 먼저 선택하겠다고 요청하면 세 모드 중 선택을 받아라. 이미 정한 모드를 반복 질문하지 마라.
- 선택·변경된 값은 파일 도구가 있으면 docs/WORKFLOW_SETTINGS.md에 짧게 기록하라. 파일이 없으면 새로 만들되 기존 설정의 다른 항목은 보존하라. 파일 도구가 없으면 대화에 기록하라.
- 아래 숫자는 자연어 기본값과 목표 예산이다. 자동 타이머나 프로그램의 강제 제한이 아니다. 실제 남은 시간을 확인할 수 없으면 사용자에게 받은 시간을 사용하고 추정임을 표시하라.
- 깊이를 줄여도 원문 필수 기능, 고정 ID, 명시적인 시안 선택, 실제 검증의 정직성은 유지하라. 시간 부족 때문에 필수 기능을 조용히 제외하지 마라.

| 모드 | 기본 시안 수 | 비교 범위와 품질 | 3시간 시험의 목표 시간 |
| --- | --- | --- | --- |
| 빠르게 | 2개 | 대표 화면 1개, 명확히 다른 구조·시각 방향, 핵심 동작 1개와 빈 상태 | 10~15분 |
| 표준 | 3개 | 대표 화면과 상세/편집 패널, 핵심 흐름 2~3단계, 모바일·빈/오류 상태 | 20~30분 |
| 깊게 | 4개 | 연결된 화면 2~3개, 한 가지 주요 사용자 여정, 상태·경계·상호작용의 완성도까지 비교 | 35~50분 |

개수·화면 수·완성도·시간 예산을 독립적으로 조정할 수 있게 하라. 예: '표준 품질, 시안 2개, 대표 화면 하나와 상세 패널, 20분 목표'. 요청한 시안 수를 임의로 줄이지 마라. 5~6개도 지정 가능하고 6개는 권장 상한이지 기술적 제한이 아니다. 그 이상은 비교 비용을 설명하고 대표 흐름을 좁히는 방법을 제안하라. 시안 수가 늘어도 서비스 전체를 후보별로 중복 구현하지 마라. 시간은 목표치이며 모델·환경·사용자 선택 시간에 따라 달라진다.

## 조정 가능한 기본값 — 표준 모드 기준

- 시안 3개, 대표 화면과 상세/편집 패널, 핵심 흐름 2~3단계. 사용자가 지정한 개수·범위·품질을 우선하라.
- 비교 페이지: 후보 요약과 비교표, 실제 화면 확대, 동일 뷰포트·데이터·상태 전환, 선택과 수정 메모.
- 산출물: docs/DESIGN_BRIEF.md, 프로젝트 관례에 맞는 비교 페이지(기본 previews/frontend/index.html), docs/DESIGN_SELECTION.md, 단계 인계.
- 후보 제시 후 명시적 선택을 기다리는 지점 1회. 이미 주어진 선택을 재승인받지 마라.

## 1. PRD를 디자인 과제로 변환

1. 최신 PRD와 기존 화면·컴포넌트·자산·실행 환경을 읽어라. 대표 사용자, 핵심 과업, 가장 중요한 행동, 우선 노출할 데이터, 관련 요구사항 ID를 추려라.
2. docs/DESIGN_BRIEF.md에 목표 화면·사용 흐름, 필수 콘텐츠·기능, 시안 간 비교할 축, 기존 브랜드·구현 제약, 개수·범위·시간 예산을 짧게 기록하라. 이 문서를 위한 별도 승인 단계는 추가하지 마라.
3. 기존 디자인 시스템이 있으면 존중하라. 참고 이미지가 있으면 색을 복제하는 데 그치지 말고 밀도·위계·배치 규칙을 분석하라. 자료가 없으면 서비스의 성격에서 합리적인 방향을 제안하고 가정임을 표시하라.
4. 질문은 결과가 크게 달라지는 미정 사항에만 한정하라. 입력이 충분하면 '원하는 색상은?' 같은 질문으로 멈추지 마라. 페이지를 만들기 위해 원문에 없는 기능을 발명하지 마라.

## 2. 후보마다 실질적으로 다른 설계 가설

- 후보마다 디자인 이름, 목표 사용자 경험, 강점·비용을 한 문장씩 정하라. 같은 레이아웃의 색상만 바꾼 후보를 다른 시안으로 취급하지 마라.
- 정보 구조·탐색 방식·화면 배치·밀도·시각적 위계·타이포그래피 중 최소 두 축에서 의미 있는 차이를 만들어라. 차이는 사용자가 과업을 수행하는 방식과 연결하라.
- 예를 들어 목록 작업이 중심이면 A는 조밀한 테이블과 고정 도구, B는 카드와 요약·상세 패널처럼 접근을 달리할 수 있다. 모든 서비스에 이 예시나 대시보드 구조를 강제하지 마라.
- 모든 후보에 동일한 필수 기능·데이터·권한·완료 조건을 적용하라. 기능이 빠진 후보와 완성된 후보를 비교하거나, 일부만 정성 들여 기본 선택으로 유도하지 마라.
- 확정되지 않은 정책을 디자인 선택으로 슬쩍 확정하지 마라. 정책 미정이 화면에 영향을 주면 표시하거나 실제 선택이 필요한 항목으로 확인하라.

## 3. 실제 제품 수준의 화면 구성

- 서비스 목적에 맞게 시선 순서와 주요 행동을 설계하라. 제목·요약·목록·보조 정보의 위계를 만들고, 모든 요소를 같은 카드·같은 크기로 나열하지 마라.
- 후보별로 제한된 색상 역할(배경·표면·본문·보조·강조·상태), 제목/본문/보조 글자 단계, 간격·모서리·테두리·그림자 규칙을 일관되게 적용하라.
- 페이지와 컴포넌트의 정렬·간격을 다듬고 읽기 폭·줄바꿈·긴 제목·숫자 정렬을 확인하라. 장식 때문에 중요한 데이터나 행동을 숨기지 마라.
- 실제 서비스에 어울리는 한국어 문구와 현실적인 샘플 데이터를 사용하라. 반복되는 'Lorem ipsum', 의미 없는 수치·차트·아이콘, 역할 없는 거대한 히어로로 화면을 채우지 마라.
- 이미지가 핵심이면 기존 자산이나 사용 가능한 적절한 이미지 도구를 사용하라. 이미지가 필요 없는 업무 도구에는 억지로 삽입하지 마라. 깨진 이미지·임시 사각형을 완성된 시안처럼 제시하지 마라.
- 입력·버튼·필터·목록·상세·대화상자를 같은 디자인 언어로 연결하라. hover·focus·선택·비활성 상태를 구분하고, 장식 애니메이션보다 명확한 조작 피드백을 우선하라.

## 4. 대표 흐름과 상태를 실제로 조작 가능하게

- 표준 모드에서는 목록 → 상세/편집 → 결과 확인처럼 대표 흐름을 연결하라. 버튼을 눌러도 반응이 없는 장식 화면으로 끝내지 마라.
- 후보별로 같은 기본/빈/오류 데이터를 전환하고 동일한 행동을 비교할 수 있게 하라. 깊게 모드에서는 관련될 때 로딩·긴 데이터·검증 실패·처리 중·복구 상태도 확인하라.
- 미리보기의 로컬 상태로 동작해도 되지만 실제 API 연동·영구 저장이 된 것처럼 설명하지 마라. 프로토타입 안내는 비교 페이지에 표시하고 최종 서비스의 일반 화면에 개발 설명을 섞지 마라.
- 키보드 탐색, 보이는 포커스, 입력 라벨, 색상 외 상태 표시, 읽을 수 있는 대비와 터치 영역을 갖추라. 필요 이상의 접근성 보고서를 만들지는 말고 실제 핵심 조작을 확인하라.
- 데스크톱·모바일에서 정보 우선순위를 유지하라. 단순 축소에 그치지 말고 탐색·목록·액션 배치를 재구성하라. 가로 넘침·가려진 버튼·사용 불가능한 패널을 확인하라.

## 5. 비교 사이트 자체의 사용성

1. 요약 카드에는 고정 후보 ID(A/B/C 등)·개정 버전, 방향 이름, 주요 차이·장단점을 표시하라. 긴 설명보다 실제 화면을 먼저 볼 수 있게 하라.
2. 두 후보를 같은 뷰포트·데이터 상태로 나란히 비교하고 각 후보를 전체 크기로 열 수 있게 하라. 모바일에서는 후보 전환과 확대를 사용하기 쉽게 하라. 좁은 썸네일만으로 선택하게 하지 마라.
3. 간단한 비교표에 정보 구조·핵심 행동·밀도·모바일 처리의 차이를 보여라. 근거 없는 점수나 가짜 사용자 평가를 만들지 마라.
4. 선택 버튼, 선택 상태, 수정 메모, 선택 요약 복사/다운로드를 제공하라. 'A 배치 + B 색상' 같은 조합 요청을 메모로 전달할 수 있게 하라. 비교 페이지 선택과 서비스의 업무 버튼을 구분하라.
5. 가능한 경우 후보 ID·버전·메모·상태를 전용 저장 키에 보존해 새로고침 후 복원하라. 앱의 실제 사용자 데이터 저장 키를 덮어쓰지 마라. 메모는 텍스트로 처리하라.
6. 화면 클릭이 AI에 자동 전달된다고 가정하지 마라. 연결 수단이 없으면 선택 ID·버전·메모를 복사해 채팅으로 보내도록 안내하라.
7. 스타일·상태·이벤트가 후보 사이에 섞이지 않게 범위를 분리하라. 기존 프로젝트 스택을 우선하고 비교만을 위해 불필요한 의존성이나 배포를 추가하지 마라.

## 6. 제시 전 확인과 선택 대기

- 가능한 도구로 페이지를 열고 후보별 실제 화면·대표 흐름, 비교/확대/뷰포트 전환, 상태 전환, 선택·메모 전달, 새로고침 복원을 확인하라.
- 같은 데스크톱·모바일 크기에서 넘침·잘림·문구·간격·읽기 어려운 대비를 점검하라. 도구가 있으면 후보별 같은 조건의 화면을 캡처해 비교하고 눈에 띄는 결함을 수정하라.
- 실제 확인한 결과와 미확인을 구분하라. 브라우저 도구가 없으면 가능한 빌드·코드 검증만 수행했다고 표시하고 화면 검증을 했다고 주장하지 마라. 존재하지 않는 URL을 제공하지 마라.
- 사용자에게 비교 페이지의 실제 주소/경로·실행법, 후보별 핵심 차이, 선택 입력 예시를 제공하라. 이때 명시적 선택을 기다려라. 추천 후보·기본 선택·시간 경과를 사용자 선택으로 처리하지 마라.
- 수정 시 후보 ID는 유지하고 개정 버전을 올려라. 재개 시 기존 후보·선택 상태부터 확인하고 무조건 다시 생성하지 마라.

## 7. 선택 결과를 구현 계약으로 전달

사용자 선택 후 docs/DESIGN_SELECTION.md와 3-build 인계에 다음을 기록하라:

- 선택 후보 ID·버전, 명시적 선택 근거, 조합·수정 메모와 적용 범위.
- 선택된 화면·흐름·상태, 관련 PRD 요구사항 ID와 소스 경로.
- 선택한 배치·탐색·정보 우선순위, 반응형 전환 규칙.
- 색상 역할, 글자 단계, 간격·형태, 핵심 컴포넌트의 스타일·상태를 재현할 수 있는 토큰 또는 실제 CSS/컴포넌트 참조.
- 미리보기 전용 데이터·미연결 기능·확인하지 못한 부분, 실제 구현 시 연결해야 할 저장/API·오류 처리.
- 사용자 수정 메모별 반영 대상과 확인할 결과.

사용자가 구현까지 요청했으면 3-build로 이어가 선택된 규칙을 실제 서비스에 적용하라. 서비스 전체 구현을 요청하지 않았다면 선택 기록과 인계까지만 완료하라. 샘플 화면을 그대로 붙여 넣고 실제 데이터·상태 연결을 끝낸 것처럼 보고하지 마라. 비교 사이트의 도구·메모·샘플 표시를 최종 서비스에 불필요하게 노출하지 마라.

## 완료 기준

선택 전에는 같은 기능·데이터로 의미 있게 다른 UI를 실제 조작·비교할 수 있고, 가능한 범위에서 화면과 흐름을 확인해야 한다. 선택 후에는 재현 가능한 디자인 계약과 다음 단계 인계가 남아야 한다. 실제 서비스 적용까지 요청받았다면 원래 요구사항과 선택된 디자인을 함께 검증하라. 비교 페이지 제공, 선택 확정, 서비스 적용 완료를 구분해서 보고하라.
