# 작업 규칙

세션 내내 적용한다. 단계별 절차는 스킬에 있다: `$1-kickoff` → `$2-prd` → `$3-core` → `$4-build` → `$5-finish`.

## 우선순위

과제 원문(README·안내) > 업무 담당자 답변 > 이 규칙. 필수 파일명·경로·기술 스택은 과제 원문을 따른다. 서로 충돌하면 임의로 정하지 말고 사람에게 알린다.

**모든 판단은 과제 원문에서 시작한다.** 이 키트의 단계, 문서, 검사는 원문을 구현하기 위한 도구다. 원문이 요구하지 않은 기능과 규칙을 키트 때문에 추가하지 않는다. 원문이 구조, 산출물, 검증 방법, 화면을 지정하면 키트의 기본값 대신 그것을 따른다. 요구사항, 결정, 방법을 제안할 때는 근거가 되는 원문 문장을 함께 댄다. 근거가 없으면 담당자 답이나 가정이라고 밝힌다.

## 게이트

통과하기 전에는 다음 단계로 넘어가지 않는다. 시간이 부족하다는 이유로 건너뛰지 않는다.

- **G1 입력:** 제공 데이터를 스크립트로 세거나, 데이터가 없으면 기존 코드·API·입력 예시를 실제로 실행해 `docs/DATA_PROFILE.md`에 남기기 전에는 설계하지 않는다.
- **G2 설계:** `docs/PRD.md`에 기준 입력, 핵심 결과의 판정 기준과 근거, 숫자 완료 조건, 멈춤 조건을 적고 사람의 OK를 받기 전에는 구현하지 않는다.
- **G3 핵심 결과:** 핵심 로직을 실행하면 바로 실제 결과를 판정 기준과 비교해 출력한다. 기준을 벗어나면 API·화면으로 넘어가지 말고 멈춰서 원인과 함께 보고한다. 기준을 바꾸려면 근거를 D 항목으로 남기고 사람의 OK를 받는다.
- **G4 증거:** 증명할 명령을 찾아 새로 실행하고 출력과 종료 코드를 읽기 전에는 완료·통과·수정됨이라고 말하지 않는다. "아마", "될 것이다"는 증거가 아니다. 서브에이전트 보고는 diff와 직접 실행으로 확인한다. 확인하지 못한 것은 미확인이라고 쓴다.

## 구현 전 대화

코드를 바꾸기 전에 어떻게 할지 먼저 말하고 사람의 승인을 받는다. 작업마다 아래 형식으로 보여주고 답을 기다린다.

```text
[T3] 할 일: (한 문장)
방법: (어떤 구조와 로직으로 만들지 2~3줄)
다른 방법: (대안 하나와 그 방법이 잃는 것)
바뀌는 파일:
확인 방법: (실행할 명령과 통과의 뜻)
추천: (고른 방법과 이유)
```

- 사람이 고치거나 다른 방법을 말하면 반영해서 다시 짧게 확인한다. 이해가 안 된다고 하면 코드 없이 설명한다.
- 사람이 바꾼 방법과 이유는 `docs/DECISIONS.md`에 적는다.
- 사람이 "다음 N개는 맡길게"처럼 범위를 정해 맡기면 그 범위만 묻지 않고 진행한다.
- 오타, 포맷처럼 동작이 바뀌지 않는 수정과 읽기, 조회, 검증 실행은 묻지 않는다.
- 승인된 방법과 달라져야 하면 멈추고 다시 묻는다.
- 서브에이전트에 맡기는 것도 맡길 범위를 먼저 승인받는다.

## 시간

타이머를 볼 수 없으니 남은 시간을 추측하지 않는다. 게이트를 넘을 때 사람에게 한 줄로 묻되, 방금 들었으면 다시 묻지 않는다. 시간이 모자라면 선택 기능, UI 장식 순으로 줄인다. 필수 요구사항을 조용히 빼지 않는다.

## 서버

- 서버는 사람이 `server` 터미널에서 실행한다. 직접 띄우지 말고 실행 명령 한 줄을 알려준다. 명령에는 `2>&1 | tee logs/server.log`를 붙인다.
- 확인은 `curl`과 `logs/server.log`로 한다. 재시작이 필요하면 사람에게 요청한다.
- 서버는 `0.0.0.0`에 바인딩한다. 미리보기는 플랫폼 프록시 주소로 열리므로 프론트의 API 호출은 상대 경로로 쓰고, 가능하면 한 포트로 서빙한다.

## 기록

- 요구사항과 완료 조건은 `docs/PRD.md`, 결정과 가정은 `docs/DECISIONS.md`, 작업·검증 결과·실수는 `docs/TASKS.md`에 남긴다. 대화에만 남기지 않는다.
- 검수를 받거나 AI 제안을 받아들이거나 버릴 때는 그 자리에서 `docs/AI_LOG.md`에 요청 원문, 처리, 근거를 적는다. 나중에 기억으로 채우지 않는다.
- 제출 문서에는 실제로 한 일과 근거가 있는 것만 쓴다. 후속 서술형은 제출물과 작업 기록을 바탕으로 출제된다.
- 게이트 통과와 작업 완료 때마다 로컬 커밋한다. G3 실패 기록도 커밋할 수 있다. 메시지에 D·R ID를 넣고, 생성 결과와 의존성은 `.gitignore`에 넣는다.
- 설계나 로직이 틀렸음을 발견하면 숨기지 말고 `docs/TASKS.md`의 "실수와 수정"에 적는다. 사소한 명령 실패는 적지 않는다.

## 위임

서브에이전트는 세션당 최대 2개다(메인 제외). 절차는 `$4-build`를 따른다. 설계와 핵심 로직은 메인이 맡는다.

## 금지

- 문제·파일·결과물의 외부 전송과 git push
- 개인 API 키·구독, 외부 AI 서비스·모델 연결, Computer Use
- 플랫폼 관리 설정, 감독·연결 프로세스의 수정·종료, 차단 기능의 우회
- 외부 코드로 결과물을 통째로 대체하기. 일부를 참고하면 출처를 남긴다.

막히면 우회하지 말고 사람에게 알린다. 플랫폼 오류는 사람이 '문제 신고'로 접수한다.
